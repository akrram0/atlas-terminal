## 1. Goals and constraints

User-visible goals (reported against v0.1.49 at 15% opacity, Classic dark,
maximized):

1. **At full size the acrylic blur must reach the screen edges** - it looked
   like it faded out near the edges.
2. **Tab names in the top bar must be clearly readable** - they washed out
   over the blurred wallpaper.

Hard constraints that stayed in force:

- The terminal area must remain fully transparent over the acrylic; only the
  chrome may gain opacity.
- No Unicode/emoji UI icons; only embedded SVGs.
- Never take control of the desktop: no SendKeys, GUI automation, screenshots,
  or focus stealing.
- Preserve all prior fixes: Git Bash -> Git for Windows, maximized frost,
  Ctrl+K palette, Ctrl+V paste, smart Ctrl+C, Classic theme, URL panic fix,
  rounded prompt corners, updater, WSL icons.
- No Windows Rust toolchain locally; CI is the authoritative build.

## 2. Bug 1 - blur fades near the screen edges when maximized

### 2.1 Root cause

The window is frameless (`WS_THICKFRAME`, no `WS_CAPTION`). Windows maximizes
such a window to the work area **plus** the resize frame and outdents it past
the screen edges. Atlas compensated by insetting the client rect in
`WM_NCCALCSIZE` by `SM_CXSIZEFRAME + SM_CXPADDEDBORDER` while zoomed. That
left a non-client ring at the screen edges: the acrylic accent only covers the
client area, so the outermost band was not blurred. DWM additionally drew its
1px window border on top of the edge.

In short: blur covered the client, the client stopped short of the edge, and
the remaining ring was unblurred.

### 2.2 Fix (`src/main.rs`, `rounded_corners`)

1. **`WM_GETMINMAXINFO` handler** (line ~712) pins the maximized rect to the
   monitor work area:
   - call the original wndproc first (`DefWindowProcW`/`CallWindowProcW`),
   - `MonitorFromWindow(hwnd, MONITOR_DEFAULTTONEAREST)` +
     `GetMonitorInfoW`,
   - set `ptMaxPosition = rc_work.origin - rc_monitor.origin` and
     `ptMaxSize = rc_work.size`,
   - keep DefWindowProc's tracking limits, with a monitor-sized fallback if a
     custom wndproc left them zero.
   The window now maximizes to exactly the work area, not past the screen.
2. **`WM_NCCALCSIZE`** (line ~755) always returns 0 and leaves `rgrc[0]`
   untouched, at every size. With the maximized rect pinned, the client covers
   the whole window, so the acrylic is full-bleed.
3. **`WM_NCHITTEST`** no longer adds a frame offset while zoomed (client ==
   window rect now).
4. **DWM border removed**: `DWMWA_BORDER_COLOR` (34) set to
   `DWMWA_COLOR_NONE` (`0xFFFFFFFE`) next to the existing corner-preference
   call. On Windows 10 the call fails and is ignored.
5. **Verification log**: on a maximize transition, `WM_SIZE` now logs
   `backdrop: maximized window WxH client WxH`; the two pairs must be equal.

`SM_CXSIZEFRAME`/`SM_CXPADDEDBORDER`, `GetSystemMetricsForDpi` and the
`NcCalcSizeParams` struct were removed as dead code; `Point`, `MinMaxInfo`,
`MonitorInfo`, `MonitorFromWindow` and `GetMonitorInfoW` were added.

### 2.3 Why this is the right layer

DWM's acrylic blur radius is fixed and there is no API to extend it. The only
way to have blur at the edge is to make the acrylic surface reach the edge.
Pseudo-maximize tricks were explicitly rejected (they break Snap, the taskbar
work area, and multi-monitor behavior).

## 3. Bug 2 - tab names unreadable in translucent mode

### 3.1 Root cause

In `src/view.rs`, the translucent chrome fill was:

```rust
let chrome = Rgba { a: (self.opacity * 0.70).clamp(0.10, 0.85), ..tb.panel_bg };
```

At the user's opacity `0.15` that is `0.105` - the 36px bar was ~10% opaque,
so a bright wallpaper dominated it. Inactive tab labels/icons used
`theme.chrome_fg` (`#8A8A8A` in Classic), which needs a dark backdrop to hold
contrast; over the wallpaper they washed out. The active pill used a
translucent hover wash that could also lose its title.

### 3.2 Fix (`src/view.rs`)

- **Chrome alpha floor** (line ~2076):
  `a: (0.56 + self.opacity * 0.34).clamp(0.56, 0.90)`.
  At 0.15 -> 0.611; at 0.999 -> 0.90; at 1.0 the opaque branch uses
  `panel_bg` unchanged. The bar stays dark in dark themes and light in light
  themes at every slider position, while the wallpaper still reads through.
- **`chrome_ink`** (line ~2053), used only while translucent:
  `lerp_color(chrome_fg, chrome_fg_active, 0.40)` - Classic becomes ~`#B8B8B8`
  over the ~61% dark bar, roughly 3:1 contrast. Opaque mode keeps the theme
  token. Applied to inactive tab title + icon, the workspace mark, the new-tab
  plus, the refresh/settings icons and the window-control glyphs.
- **Active pill hover** (lines ~2152 and ~2281): in translucent mode the
  active pill hovers to an opaque `lerp_color(elevated_bg, accent, 0.10)`
  instead of translucent `card_hover`, so the active title never sits on a
  wash. Inactive pills keep `card_hover`.
- Sheet and container remain fully transparent (`rgba(0x00000000)`); the
  terminal area is untouched.

Light-theme note: `panel_bg` is light there, so the same floor keeps a light
bar; `chrome_fg` -> `chrome_fg_active` darkens the inactive ink. The logic is
theme-agnostic (no hard-coded black/white).

## 6. Limits and next steps

- Windows does not round maximized windows; `DWMWCP_ROUND` only affects
  restored windows. That is unchanged and expected.
- DWM's blur radius is fixed; v0.1.50 fixes coverage, not radius.
- If the chrome bar now reads too heavy at low opacity, tune the `0.56` floor
  in `src/view.rs` (keep it >= ~0.50 for 3:1 tab contrast). If the bar reads
  too light, raise it.
- If a multi-monitor setup shows the wrong maximize size, check
  `MonitorFromWindow(MONITOR_DEFAULTTONEAREST)` in the `WM_GETMINMAXINFO` arm;
  the rect is in physical pixels and is DPI-correct by construction.
- OpenCode prompt corners remain an upstream limitation; the local
  `atlas-glass` theme notes from v0.1.49 still apply
  ([`2026-10-23-v0.1.49.md`](2026-10-23-v0.1.49.md)).
